# 顧客情報・30分値連携のケース別テストデータ

`prepare_link_customer_30min_cases.py` は、次の仕様書の項番1～72に対応する入力データを準備します。

- `docs/PG2-1-01_単体テスト1ケース・結果一覧表_顧客情報と30分値データの連携機能バッチ.xls`
- シート「単体テスト1ケース・結果一覧表」の8～79行

ケースID、Excel行番号、手順、予想結果は `link_customer_30min_cases.json` に保存しています。
実行時にExcelやxlrdは不要です。Python 3.12と既存バッチのSQLAlchemyを使用します。
元のExcelは変更しません。仕様書を変更した場合はカタログと生成処理の対応を見直してください。

## 使い方

プロジェクトルートから実行します。まずケース一覧を確認します。

```powershell
Set-Location C:\STEP4\electricity_report
python -m cndx_corp_batch.test.prepare_link_customer_30min_cases --list
```

DB接続せずに、ケース72（トランザクション）の投入計画を確認・保存する例です。
JSONには全テーブルの投入レコード、供給地点、対象年月、バッチ実行コマンド、実行時の環境変数、予想結果、注意事項が含まれます。
日時や識別子は固定のため、同じケース・開始番号から同じ計画が得られます。

```powershell
python -m cndx_corp_batch.test.prepare_link_customer_30min_cases `
    --case 72 --dry-run --output output/link_customer_30min/case72.json
```

テスト用PostgreSQLへ投入する例です。接続設定は既存の `test/database.json` と共通です。
ケースごとに初期化済みの検証DBを使ってください。バッチは他ケースの未処理行も取得するため、
複数ケースを混在させると件数や異常系の結果が変わります。PGは既存データを削除しません。

```powershell
$env:REPORT_DATABASE_URL = 'postgresql+psycopg2://ユーザー:パスワード@ホスト/検証用DB名'
python -m cndx_corp_batch.test.prepare_link_customer_30min_cases `
    --case 72 --db-config cndx_corp_batch/test/database.json `
    --output output/link_customer_30min/case72.json

# 投入先と同じDBで、batch_environmentを設定してbatch_commandを実行する。
$env:DATABASE_URL = $env:REPORT_DATABASE_URL
$env:CUT_OFF_DAY = '16'
$env:REPORT_MONTH_OFFSET_BEFORE = '3'
$env:REPORT_MONTH_OFFSET_AFTER = '2'
python -m cndx_corp_batch.entrypoints.link_customer_30min `
    --batch-date 2026-08-19 --batch-size 10
```

このPGはバッチ本体を自動実行しません。投入に成功すると「投入完了」と各テーブルの件数を表示します。
`--output` のJSONは投入前に保存する計画であり、投入成功やテスト合格の証跡ではありません。
バッチ本体は環境設定で対象月を決めます。新版仕様書の15日／16日の境界を検証する際は、
`batch_environment` に出力した上記3変数を設定してください。PGは親シェルの環境変数を変更しません。

既存キーがあればエラー終了し、上書き・スキップはしません。投入途中で失敗した場合も全INSERTをロールバックします。
別番号で用意する場合は `--start-id 90001` のように指定できますが、既存の未処理行との混在には注意してください。
同じ開始番号を指定すると他ケースでも同じキーになるので、通常はケースごとの既定値を使います。

## 生成内容とケース対応

取込管理、企業基本情報、建物、ARVEお客さま情報、EP30分値を作成します。
1供給地点につき対象月の1日分・48コマを用意します。基本値はコマ順に文字列の `1`～`48` で、
値変換ケースでは指定列だけを変更します。更新ケースでは連携先の生データにも更新前の1行を作成します。
供給地点は `999901` から始まる22桁、その他のキーも架空の値です。
DBの列名の大文字・小文字は吸収します。必要な列が欠けている場合は投入前にエラーにします。

| ケースID | 準備する条件 |
| --- | --- |
| 1、10、14、17、20、25～34、37、40、56～60、65、66、68、70 | 正常な1地点。項目転記・初期値・再実行などを確認 |
| 2、19 | 0件。検証DBに別の処理対象がないことを確認して実行 |
| 3～9 | 仕様書の実行日と、それに対応する対象月のデータ |
| 11 | 状態4 |
| 12、13 | 対象年月不一致。13は紐付け日時も設定 |
| 15、16、18 | 建物なし、建物削除TRUE、建物の供給地点不一致 |
| 21～24 | 9、10、11、21地点。取得件数を10にして確認 |
| 35、36、38、39 | ARVE元番号が `012`、`0123`、`012`、`01` |
| 41～45 | 欠測件数が `12`、`0`、空文字、`AB`、`-1` |
| 46～50 | 不正値件数が `12`、`0`、空文字、`AB`、`-1` |
| 51 | 48コマすべて異なる整数文字列 |
| 52～55 | 電力量1が `0.12`、`0`、空文字、`AB` |
| 61～64、67 | 更新前の生データあり。48コマは999、作成者はpg2_original、作成日時は2000-01-01 |
| 69 | 取込管理の紐付けエラーメッセージに前回エラーを設定 |
| 71 | 電力量1をABにして数値変換エラーを発生させる |
| 72 | 15地点。昇順の先頭10地点は正常、残り5地点の電力量1はAB |

新版では連番の重複が解消されたため、すべて枝番なしの項番で指定します。
作成者・更新者のケースは次の対応になりました。

| 新ID | 旧ID | Excel行 | 確認項目 |
| --- | --- | --- | --- |
| 57 | 59-1 | 64 | 新規登録時の作成者 |
| 58 | 59-2 | 65 | 新規登録時の作成日時 |
| 59 | 60-1 | 66 | 新規登録時の更新者NULL |
| 60 | 60-2 | 67 | 新規登録時の更新日時NULL |
| 61 | 59-3 | 68 | 更新時の作成者保持 |
| 62 | 59-4 | 69 | 更新時の作成日時保持 |
| 63 | 60-3 | 70 | 更新時の更新者 |
| 64 | 60-4 | 71 | 更新時の更新日時 |

旧版の状態NULL・紐付け日時空文字のケースは削除されています。
旧枝番（59-1など）は受け付けません。旧番号の数値を指定すると新版の別ケースになる場合があります。
旧版で保存した計画JSONや投入済みDBは再利用せず、ケース一覧を確認して新しい計画・検証DBを用意してください。

## 仕様書・DB定義・現行実装の差異

- **3～9**：新版仕様書の対象月は15日までが3か月前、16日以降が2か月前です。PGもこの条件で生成します。現行設定の省略値はCUT_OFF_DAY=15のため、仕様書の境界と一致させるにはCUT_OFF_DAY=16を明示してください。
- **13**：手順に従い対象年月も不一致にしています。紐付け日時だけによる除外を検証するケースにはなりません。
- **45・50**：現行SQLのINTEGERへのCASTは負数を許容します。非負制約がないDBでは、仕様書の「エラーになる」という期待と結果が異なります。生成値は仕様書どおり-1です。
- **52～55**：手順欄は「不正値時間帯_件数」となっていますが、テスト内容欄の「V30分_使用_電力量_1」を優先し、T01_30T_SYR01を変更します。
- **65**：ファイル更新日時の期待は空文字ですが、日時型のため現行SQLはNULLを登録します。
- **70**：データ準備後にバッチを2回実行します。PGを再投入する必要はありません。
- **71・72**：PostgreSQLのCASTエラーを利用します。72は `--batch-size 10` で、先頭10地点の登録・紐付けが確定し、後半5地点の生データは登録されず、管理行にはエラーが残ることを確認します。

## ローカルでの投入確認

SQLite用の設定JSONを作成して、投入処理のみを確認できます。

```json
{
  "url": "sqlite:///output/link_customer_30min/case51.db",
  "schema": null
}
```

上記を `output/link_customer_30min/sqlite.json` に保存した場合：

```powershell
python -m cndx_corp_batch.test.prepare_link_customer_30min_cases `
    --case 51 --db-config output/link_customer_30min/sqlite.json --init-sqlite
```

`--init-sqlite` は最小限のテーブルを作ります。PostgreSQLには使用できません。
SQLiteのCASTは空文字・ABを数値0に変換するため、異常系の実際の結果確認にはPostgreSQLが必要です。
通常のバッチ起動コマンドもPostgreSQL向けです。SQLiteでのバッチ確認は以下の自動テストで行います。

```powershell
python -m pytest cndx_corp_batch/tests/test_link_customer_30min_cases.py `
    cndx_corp_batch/tests/test_link_customer_30min_seed.py `
    cndx_corp_batch/tests/link_customer_30min -q
```

自動テストでは72行の対応、全72ケースの投入、抽出条件・年月境界、ページ分割、番号分割、
48コマの転記、UPSERT、再実行、投入失敗時のロールバックを確認します。
ケース72のトランザクション検証ではSQLiteのトリガーでDBエラーを代替します。
項番3～9は、生成日付・対象月に加え、投入計画の環境設定を渡した本体との連携を検証します。
PostgreSQL固有のCAST、行ロック、実環境の追加制約は実DBで確認してください。
